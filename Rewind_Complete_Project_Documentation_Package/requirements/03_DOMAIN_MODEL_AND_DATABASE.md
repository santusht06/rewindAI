# 03 — Domain Model and Database

## 1. Design principles
Use stable IDs, foreign keys, unique constraints, explicit lifecycle states, UTC timestamps, migrations, and transactional boundaries. Avoid storing derived state when it can be recomputed safely. Exact types and indexes depend on the selected database and repository evidence.

## 2. Core entities
### User
`id`, authentication subject/provider ID, status, created/updated timestamps, privacy preferences. Do not store a password if identity is delegated to a trusted identity provider. If local credentials are approved, use a reviewed password-hashing scheme; never plaintext or reversible encryption.

### Title
`id`, canonical title, release year, type, language/region metadata, publication state, rights/authorization reference, created/updated timestamps. Add unique constraints for verified external IDs where appropriate. A title is not publishable until content rights and index validation pass.

### ContentAsset
`id`, `title_id`, asset type, source reference, source checksum, source version, rights status, locale, parser version, ingestion status, created time, retention/deletion state. Do not assume the system may store full video. Prefer authorized transcript/subtitle assets or approved metadata.

### IngestionRun
`id`, `asset_id`, idempotency key, configuration fingerprint, state, started/completed timestamps, counts, sanitized error code, operator/trigger reference. Unique constraint on idempotency key or equivalent deduplication strategy.

### ContentChunk
`id`, `title_id`, `asset_id`, `index_version`, ordinal, start/end timestamp, text, normalized text/hash, locale, speaker/scene metadata if reliably available, provenance. Unique key should prevent duplicate chunks for the same asset/version/ordinal. Validate `start_ms >= 0`, `end_ms >= start_ms`.

### Embedding
May be a column on `ContentChunk` or a separate table, depending on model/version and database capability. Store embedding model/version, dimensions, vector, and chunk reference. Do not mix vectors from incompatible models in the same search space.

### PublishedIndex
`id`, `title_id`, `index_version`, status, chunk count, embedding model/version, parser version, published timestamp, previous valid version. Only one active version per title unless multi-version serving is intentionally designed.

### ViewingSession
`id`, `user_id`, `title_id`, status, progress milliseconds, progress source, progress confidence/verification, last progress update, locale, spoiler mode, spoiler consent scope/expiry if applicable, created/updated timestamps. Validate progress against known duration when duration is reliable. Do not treat a client-supplied value as verified integration data.

### Question
`id`, `session_id`, request ID/idempotency key where appropriate, normalized question hash, status, answer metadata, model/prompt version, latency, token/cost metrics. Define retention and whether raw question text is stored; default to minimizing it.

### RetrievedEvidence / AnswerCitation
Persist only if needed for auditing/evaluation and under a documented retention policy. Reference real chunk IDs, timestamps, and index version. Never accept citation IDs generated by the model as authoritative.

### AuditEvent
`id`, actor, action, target type/id, timestamp, correlation ID, outcome, sanitized metadata. Never include secrets or unnecessary transcript/question text.

## 3. Relationships
- User 1—N ViewingSession.
- Title 1—N ContentAsset.
- ContentAsset 1—N IngestionRun.
- Title/asset/index version 1—N ContentChunk.
- ContentChunk 1—N embedding versions only if model versioning is separated.
- Title 1—N PublishedIndex versions; exactly one active version per title in the baseline.
- ViewingSession 1—N Question.
- Question 1—N AnswerCitation if citation persistence is enabled.
- AuditEvent references an actor and target without requiring destructive cascade deletion.

## 4. Data integrity invariants
- Foreign keys MUST protect relational consistency.
- Published chunks MUST belong to a verified, active index version.
- A failed reindex MUST NOT deactivate the last good index.
- A citation MUST reference a chunk actually retrieved for that request and still be valid for the request's index version.
- User-owned sessions MUST not be queryable by another user.
- Progress cannot be negative; timestamps must be monotonic where applicable.
- Ingestion retry MUST not duplicate logical chunks.
- Rights revocation MUST trigger a documented unpublish/cache-invalidation/deletion workflow.
- Cascade deletion must be intentional; audit records may require retention without personal data.

## 5. Indexing and query considerations
Candidate indexes: session owner/title/status; asset/title/status; chunk title/index version/time range; ingestion idempotency key; question session/time; audit actor/time. Use a vector index only after validating the chosen database extension, vector dimension, query operators, migration support, and hosting constraints. Hybrid retrieval may combine vector similarity with full-text/BM25-style search. Measure retrieval quality before adding reranking.

## 6. Migrations and recovery
- Schema changes are migrations, not ad hoc production SQL.
- Back up before destructive migrations.
- Use expand-migrate-contract for rolling deployments when compatibility matters.
- Test migrations against realistic data volume and a clean database.
- Document rollback limitations when a migration is irreversible.
- Do not run destructive migration or purge without explicit approval.
